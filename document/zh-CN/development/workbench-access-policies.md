# 工作台应用目录与布局策略

工作台目录使用 `GET /v1/workbench/catalog`。响应包含当前用户可发现的应用、有限可用性原因、管理员默认入口及强制入口。目录为私有响应，不用于公共缓存。

权限沿用既有个人→角色→团队→系统解析。个人 `allowed_apps: null` 或缺省继承角色/团队；空数组不发现该权限域内的应用；个人 `"*"` 覆盖角色/团队限制。既有权限域为计划、批量、自动化和外部应用。聊天、项目、文件、设置不因空数组消失。实验室和部署模式保留各自规则，创建权限不代替阅读权限。现有提示词中心权限配置和工具栏规则保留。

每次 `POST /v1/workbench/applications/{key}/launch` 重新检查当前用户。未知或不可发现的 key 返回 404，不泄露名称；可发现但停用或当前环境不可运行时返回 409 和有限原因。目录、固定入口或管理员配置权限均不能授予运行权限。个人 API Key 仍受自身能力与应用可见范围约束；项目/智能体专用 Key 沿用既有路由限制。

## 管理员配置（商业版 EE）

系统配置台的应用配置页面提供“工作台布局策略”。管理员选择默认入口，调整默认入口顺序，配置必要强制入口或隐藏入口。布局策略仅影响工作台发现和打开，不自动成为旧业务 REST 接口的执行权限。旧计划、批量、自动化接口继续使用原认证、所有权和能力检查。

受信任的固定工具（对话、设置、帮助、计划和批量命令）不能被此布局策略移动或隐藏。插件不能声明或通过策略接口伪造强制入口。当前布局支持现有侧栏页面和已配置外部应用，个人固定/排序由后续导航偏好能力处理。

- `GET /v1/workbench/admin/catalog`：完整管理选项。
- `GET /v1/workbench/admin/policy`：读取策略和 revision。
- `PUT /v1/workbench/admin/policy`：提交 revision、defaultPinned、forced、hidden；并发版本不符返回 409。
- `GET /v1/workbench/admin/legacy-config`：受保护的完整旧应用配置。
- `GET /v1/workbench/admin/audit`：脱敏配置审计。

策略保存在独立 ContentBlock 键 `workbench_policy`。策略和审计同事务提交，不改变历史数据库迁移。初始 revision 为 0，保持原布局；配置后按已保存的默认/强制布局投影。未固定的已有页面仍在更多菜单或经典侧栏用户菜单中可访问。重启保留策略；冲突需明确重新加载，不能静默覆盖。

旧公共文档响应的应用配置按用户过滤；其他公开文档内容保留。权限配置选择器使用受保护管理目录，保留 `prompt_hub` 等原权限选项。普通新增外链不传宿主凭据；旧外链只在经过重新鉴权的旧适配路径保持原登录参数。基础 CE 目录不读取 EE 团队/角色表。

## 验证

隔离环境中的 `test_workbench_policy_routes.py` 覆盖继承、撤销、布局、直接 launch、未知 Key、API Key、SQLite/PostgreSQL 并发，以及 CE 最小表边界。前端 `npm run test:workbench-policy-browser` 使用真实 HTTP 和 Chromium 验证管理、两种侧栏、账号切换、冲突、重启及失效响应。其 mock 认证身份不等同于正式会话登录或原生桌面端验证。
