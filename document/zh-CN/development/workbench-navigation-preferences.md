# 模块导航与应用目录

侧栏负责模块切换。应用中心负责发现和打开具体应用。二者不共用固定列表。

现代模式和经典模式各自有一套模块排布，保存在页面配置 `navigation.layouts.modern` 和 `navigation.layouts.classic`。每套排布包含 `sidebar_items`（一级导航，按顺序显示）和 `more_items`（「更多」菜单，按顺序显示）；两处都不出现的模块不显示。管理员在 Config →「页面配置」→「侧边栏布局」里按模式分别调整，用户在设置里选择哪种侧边栏排布，就显示对应的配置。未配置时两种模式都使用出厂排布：一级导航为「我的空间、定时任务、能力中心」，「更多」为「项目、站点、应用中心、实验室」。实验室权限（`lab_enabled`）关闭时隐藏实验室，站点权限（`sites_enabled`）关闭时隐藏站点，两者互不影响；本机单机模式不显示我的空间；定时任务继续受用户权限控制。「设置」固定在用户头像菜单中，不参与排布。旧字段 `sidebar_items` / `menu_items` 只供工作台布局策略桥接，侧栏不再读取。

进入「更多」中的任一模块后，现代布局显示对应的二级边栏。二级边栏使用同一份模块列表，并标记当前页面。刷新保留模块导航；桌面上从「更多」再次选择模块会展开已收起的边栏。经典布局使用同一份模块模型，主侧栏显示文字入口，模块内容使用独立的二级栏。

插件应用、外部应用和具体场景应用只在应用中心展示。应用中心恢复图标、名称、说明的卡片宫格，只呈现计划模式等命令、插件和外部应用；保留来源、不可用状态和原有打开方式。侧栏和用户菜单不列出具体应用。页面设置只负责经典/现代排布的选择、确认和保存，不提供应用固定或排序控件。

## 代码边界

`utils/pageConfigDefaults.ts` 定义有限的模块集合 `MODULE_KEYS`、出厂排布和排布归一化（去重、丢弃未知 key、一个模块只出现一处）。`components/sidebar/moduleNavigation.ts` 按排布和可见性生成一级导航与「更多」。`useModuleNavigation` 只读取当前侧边栏排布对应的页面配置、用户权限和部署模式，不读取工作台应用目录或应用导航偏好。`MoreModules` 和 `ModuleSecondaryNavigation` 共用这个模型。

`applicationEntries.ts` 把服务端应用目录转换为应用中心的视图数据，不再返回侧栏模型。新增应用声明、应用数量、应用布局策略和旧固定记录均不能改变模块导航。删除旧的混合导航、应用溢出菜单、导航管理器和前端偏好客户端；不增加旧版回退或兼容开关。

服务端公开的 GET/PUT `/v1/workbench/me/navigation-preferences?environment=web` 契约未在本次前端修复中修改。认证、环境隔离、revision 并发校验和已有记录继续由服务端负责；当前侧栏不读写此接口。应用目录的访问控制和启动校验仍由服务端执行。

## 回归检查

在前端目录运行 `npm run test:sidebar-navigation`。检查实际菜单与二级边栏、刷新和收起后重开、经典与现代排布、应用卡片与打开、不可用状态、权限、本机模式，以及大量应用和旧固定策略的隔离。原模块导航测试继续检查能力分类、任务归属和移动端抽屉。

`.github/workflows/sidebar-navigation.yml` 在相关前端和共享包的 PR，以及开发/产品分支 push 时运行。它不触发部署。是否将该检查设为分支保护的必需检查，由仓库管理员配置。
