# 工作流后台作业

run_job 将脚本交给沙箱的受管理进程接口执行。提交时先准备独立执行目录，再等待 runner 的运行回执；命令提交成功本身不代表作业已启动。准备阶段最长 90 秒，运行回执通常在 30 秒内确认；外部调用也有超时，失败会写入状态和错误原因。

后台监控固定在应用生命周期的事件循环上。工具调用所在的临时线程退出、前台等待超时、用户停止当前对话，均不会自动取消已提交的作业。取消作业使用该次执行的精确句柄；不通过进程名查找或批量杀进程。

每次执行保存独立 attempt、owner、租约和沙箱进程引用。OpenSandbox 支持新 worker 接管已有命令；只有租约过期的作业才参与自动接管。无法确认旧命令状态时标记 interrupted，撤销旧回调权限，不自动重复业务。其他提供方若不支持持久进程引用，同样采用此保守处理。

显式 resume 仅在旧进程已确认退出或尚未启动时允许。runner 使用新的回调 token，SDK 的 job.map 保留台账里 done 和 not_found 项的结果，只处理其余项。此机制不保证任意脚本外部副作用的恰好一次执行：脚本自行执行的写入仍须幂等。

旧版通过脱离管理的后台 shell 启动作业，没有可靠进程引用。这些作业不能直接安全续跑；取消会撤销权限并明确告知进程状态未确认。确认旧进程已经结束后，再显式新建作业。

内部回调将鉴权与台账写入放在同一个行锁事务里，避免旧 token 在续跑后继续写入，以及并发更新互相覆盖。运行器先原子写入终态回执，再发送终态回调；即使终态回调失败，监控也能根据回执收尾。

## 验证

相关单元与回归测试位于 src/backend/tests/orchestration/test_job*.py。显式真实沙箱测试位于 src/backend/tests/integration/job_managed_smoke.py，需指定现有作业作为沙箱上下文。它创建合成作业和临时回调端口，验证并发台账、线程退出、精确取消、跨进程接管、续跑和启动失败，不调用模型，不重新执行原始业务脚本。

部署前须确认容器真正挂载的源码目录。工作区改动与运行容器的源码可能来自不同 checkout；仅重启错误挂载的容器不能使修改生效。
