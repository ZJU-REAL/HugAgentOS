# 随发行版自带的沙箱运行器

这个目录用来放**发行版自带的 bubblewrap**。放一个可执行的 `bwrap` 在这里，Linux 沙箱在
系统本身没装 bubblewrap 时就会用它，而不是拒绝执行命令。Codex 用
`codex-resources/bwrap` 解决同一个问题。

```
src/backend/resources/sandbox/bwrap        # 可执行，静态链接
```

## 查找顺序（`core.sandbox.oslayer.bwrap.resolve_bwrap`）

1. `PATH` 上的系统 `bwrap` —— **优先**。它是发行版在维护、会跟着安全更新走的那一份，
   用它意味着 bubblewrap 的补丁不需要我们重新发版就能到位。
2. 本目录里的这一份 —— 只在系统没有时才用。它是**给装不上包的机器兜底**，不是首选。
3. 两者都没有 → 沙箱后端报「不可用」，除「完全放开」外的权限档拒绝执行本机命令。
   不存在"没有沙箱就裸跑"这条路。

## 为什么默认是空的

二进制文件要不要进仓库，是发布方的决定，不该由代码顺手替你做：

- 需要**按架构各出一份**（x86_64、aarch64），少一个架构就等于那批机器没兜底；
- 静态链接的 `bwrap` 要自己构建并持续跟进上游安全更新——它是个 setuid 相关的敏感组件，
  仓库里躺着一份长期不更新的副本，比没有更危险；
- 绝大多数 Linux 用户走一键安装器，它已经会用系统包管理器装好 bubblewrap，装不上就
  当场失败，不会留到运行时才发现。

所以代码把「能用自带的」这条路准备好了，具体要不要带、带哪几个架构，由你决定。

## 要带的话怎么做

按目标架构各构建一份静态 `bwrap`（上游：<https://github.com/containers/bubblewrap>），
放进本目录并 `chmod +x`。构建产物应随发行版打包一起分发，并记录它对应的上游版本，
以便跟进安全更新。
