# 桌面双模式「云端为主 + 本机执行」混合架构设计

## 目标（用户需求）
1. 双模式下**只用一套云端用户体系**——本机端不再有独立登录/用户。
2. 「我的空间」在云端身份下正常显示。
3. **会话默认存云端**（云端项目的对话进云端库）。
4. **只有「本机端构建的本地项目」的会话与数据留在本机**。
5. 切换不再把桌面端踢出去重新登录。

## 核心思路：桌面端做「按请求路由」，两套后端各自不变
不改后端「进程级本地/云端全局开关」这一深层假设（那是数周级重构、高风险）。改为：
- **云端后端**（`:13002`）= 控制面：身份、我的空间、云端项目、云端会话。**保持原样**。
- **本机后端**（`:32101`）= 本地执行面：**仅**服务「本地文件夹项目」（其对话/文件/工具执行都在本机），且**以云端用户身份运行**。
- **桌面反代**（Rust `proxy_handler`）= 路由器：每个 `/api` 请求按上下文选云端或本机。默认云端；仅「本地项目作用域」的请求走本机。

两套后端各自仍是单一模式（云端=云端模式、本机=本地模式），因此后端的全局单例/单库假设**不被触碰**。新增工作集中在：反代路由、身份桥接、前端合并本地项目列表。

## 组件与改动

### P1 · 桌面反代基础（Rust，`desktop/src-tauri/`）
- `ProxyState` 持有**两个 live 上游**：`cloud_base` 与 `local_base`（`127.0.0.1:32101`）。
- `proxy_handler` 增加路由分支：默认转云端；当请求带 `x-hugagent-target: local`（或命中本地项目路径前缀）时转本机。
- **凭证按上游分别注入**：云端请求注入云端 session cookie；本机请求注入本机凭证（见 P2 身份桥接）。
- 双模式下**常驻启动本机后端**（解除 `lib.rs` 仅 Local 模式才启动的 gate）。
- 新增 `ProvisionMode::Hybrid` 语义（或让 `Dual` 默认云端为主、本机常驻），**运行时切换不再 `restart()`**。

### P2 · 身份桥接（本机后端以云端用户身份运行）
- 登录云端后，桌面拿到云端 `user_center_id`（+ token）。
- 本机后端启动时接收云端身份：用云端 `user_center_id` **seed 本机 shadow user**（`get_or_create_user_shadow` 正是按 `user_center_id` 归一），从而本机项目/会话归属同一用户。
- 机制候选：`core/auth/desktop_ticket_store.py`（云端签票→本机 `validate_session` 接受），或 API-key（`sk-jx-…` 在所有 AUTH_MODE 下都能 resolve）。选定后写入本机启动 env（当前 `local_server.rs` 未传任何身份 env，需补）。

### P3 · 前端（合并本地项目 + 标记本地请求）
- 侧边栏项目列表 = 云端项目（云端）+ 本地项目（本机）合并。
- 打开本地项目时，SPA 给该项目作用域的请求打 `x-hugagent-target: local`，供反代路由。
- 我的空间/云端 UI 不受影响（默认云端）。

### P4 · 数据归属（多为自然结果）
- 云端项目对话 → 云端库（现状）。
- 本地项目对话/文件/执行 → 本机（本机后端本就本地 SQLite + host 执行 + 本地策略闸门）。
- 因为按后端路由，各自存各自的库，**无需跨库/双引擎**。

## 立即可见的修复（P1 附带）
- 我的空间：改 `Sidebar.tsx` 的隐藏条件——仅在**纯本机模式**隐藏，双模式/云端一律显示。
- 双模式默认落云端身份，不再被迫走本机独立登录。

## 关键权衡 / 风险
- 路由判别子（header vs 路径前缀）需前端配合；先用 header，简单可控。
- 「所有对话历史」等跨项目聚合视图，需前端合并两端来源（P3）。
- 本机后端以云端身份运行的桥接是新契约（P2），需后端小改。
- 不做「单后端服务两类项目」，从而**绕开**后端全局单例/单库/双 FK 的重构地雷。

## 分阶段交付
P1 桌面反代双上游 + 常驻本机 + 我的空间显示（Rust/前端小改，可独立测）→ P2 身份桥接 → P3 前端合并本地项目 → P4 验证数据归属。每阶段独立提交、可回退。
