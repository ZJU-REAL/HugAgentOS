# HugAgentOS Desktop for UOS 1070 (Electron 43)

> [简体中文](README.md)

`desktop-uos/` is the dedicated release line for **UOS 1070, aarch64, and glibc
2.28**. It pins Electron `43.4.1`, produces Debian `arm64` `.deb` packages only,
does not depend on WebKitGTK 4.1, and does not treat a regular AppImage as the UOS
compatibility deliverable.

The existing Tauri 2 client in `desktop/` remains the Windows, macOS, and verified
Linux x86_64 release line. Both clients reuse the React application, CE service
archive, Python dependency profile, and backend authentication/update endpoints.

## Ported capabilities

- Local, cloud, and dual-mode provisioning; dual mode keeps cloud identity with a local execution plane.
- Full packages may set a brand-level first-launch default; fixed dual-mode distributions go straight to one-action initialization without asking for the mode again.
- `hugagent://` deep-link authentication, one-time ticket redemption, persisted session, and logout cleanup.
- Loopback proxy, cookie injection, streaming SSE, and backend file/site/docs routes.
- Local-project request routing, identity bridge, model synchronization, and capability-token refresh.
- A menu-less window matching the compact macOS client layout while retaining native
  title-bar controls, plus tray, remembered close action, and `Ctrl+Shift+Space` quick ask.
- Native folder selection/grants, file-manager opening, and background task notifications.
- Offline CPython 3.11 payload verification, safe extraction, atomic activation, data backup, and rollback.
- `.deb` update checks, SHA-256 verification, privileged UOS installation, and restart.

The initialization flow now matches the existing desktop client with halo, orbit,
and progress-highlight motion. It shows only the current stage, percentage, and
actionable errors; raw logs remain in the local-service log directory for diagnosis
instead of appearing at the bottom of the page. Set
`JX_DEFAULT_PROVISION_MODE=local_only|cloud_only|dual` to override the distribution default.

The renderer uses context isolation and the Chromium sandbox with Node integration
disabled. A narrow preload bridge exposes logout only. Renderer-provided cookies and
desktop bridge headers are stripped and regenerated by the main process.

## Build targets

| Command | Builder | Output | Local mode |
|---|---|---|---|
| `npm run build` | Native Linux aarch64, preferably UOS 1070 | Full ARM64 `.deb` | Yes |
| `npm run build:thin` | Linux x86_64 or aarch64 | Remote-only ARM64 `.deb` | No |
| `npm run pack:thin` | Linux x86_64 or aarch64 | Unpacked app | No |

Full builds intentionally reject x86_64 hosts. The Electron shell can be
cross-packaged, but the private Python runtime and binary wheels must execute their
smoke tests on aarch64. The runtime lock is
`desktop/requirements-desktop-linux-aarch64-py311.lock` and resolves against
`aarch64-manylinux_2_28`.

## Build

The builder needs Node.js `>=22.12`, Python `>=3.11`, uv `0.11.33`, `dpkg-deb`,
`file`, and `readelf`. A full build needs network access to obtain locked wheels;
the installed application never contacts PyPI during first launch.

```bash
cd desktop-uos
npm install
npm test
npm run build        # native aarch64 full package
npm run build:thin   # cross-package the remote-only ARM64 shell
npm run verify:deb -- "dist/HugAgentOS UOS_0.5.17_uos1070_arm64.deb"
```

`dist/` contains the `.deb` and `latest-uos.json`. Verification checks Debian
architecture, the glibc 2.28 dependency floor, the AArch64 ELF, the highest imported
GLIBC symbol, and packaged web resources.

## Publish updates

```bash
cd desktop-uos
npm run release:manifest -- \
  --deb "dist/HugAgentOS UOS_0.5.17_uos1070_arm64.deb" \
  --existing /path/to/current/latest.json \
  --output /path/to/desktop_release --notes "UOS ARM64 update"
```

The command copies the `.deb` and merges its SHA-256 into the shared `latest.json`
inside `--output`. Synchronize that directory to the backend `DESKTOP_RELEASE_DIR`. The UOS
client rejects entries without SHA-256, non-`.deb` artifacts, and non-aarch64 keys.

## Electron 43 lifecycle

Electron 43 is a compatibility baseline, not indefinite upstream support. Its
official end of support is scheduled for January 2027. Production maintenance must
track the latest 43.x patch monthly while qualifying Electron 44+ against UOS 1070
and the glibc 2.28 baseline.
